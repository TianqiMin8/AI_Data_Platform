3-1
### 实现对话历史接口
    要求：
    - 实现 `GET /api/v1/conversations/{id}/messages`
    - 返回该对话的所有消息（按时间排序），包含 role / content / created_at
    - 如果消息关联了 QueryExecution，同时返回 generated_sql / execution_ms / row_count

- 如果一个对话有 1000 条消息，这个接口要不要分页？用 offset 还是 cursor？
    我认为需要分页。用cursor，因为对话记录一般是先显示最新消息，然后加载更早消息，所以使用Message.id作为cursor。cursor在大数据量下更加稳定。

- 前端展示对话历史时，assistant 消息里的 SQL 应该用代码块渲染。你会在后端格式化还是前端格式化？
    前端。后端应该仅返回生成的sql而非具体展示格式。这样能保证前后端职责分离。

3-2
### 实现对话列表接口
    要求：
    - 实现 `GET /api/v1/conversations`
    - 返回当前用户的所有对话（按更新时间降序）
    - 每个对话附带最后一条消息的摘要（前 100 个字符）
    - 支持分页

- “最后一条消息的摘要” 你会在查询时 JOIN 取出来，还是在 Conversation 表加一个冗余字段？各有什么优劣？
    我会在 Conversation 表加一个冗余字段。优点是查询对话列表时非常快，不需要额外 JOIN；缺点是增加了数据冗余，而且需要保证写入 Message 时同步更新该字段，否则可能出现数据不一致。
    在查询时 JOIN 取出来的优点是数据始终以 Message 表为准，不会出现冗余数据不一致的问题；缺点是查询会更复杂，在对话数量很多时性能可能较差。

3-3
### 给 LLM 适配层加一个 StubAdapter
    要求：
    - 新增 `app/llm/stub_adapter.py`，实现 `BaseLLMAdapter`
    - `generate()` 返回固定的 SQL：`SELECT 1 AS test`
    - 在 `.env` 中加 `LLM_PROVIDER=stub` 时使用 StubAdapter
    - 修改 `factory.py` 支持根据配置切换

- StubAdapter 在什么场景下有用？（提示：测试、CI/CD、演示）
    在测试、CI/CD 和演示场景中很有用。它不需要调用真实的 LLM API，
    因此不会产生 API 费用，也不会受到输出随机性的影响。固定输出可以让自动化测试保持稳定和可重复，在演示环境中也能避免外部 LLM 服务异常导致功能不可用。

- 如果你要测试 “LLM 返回了一个无效 SQL” 的场景，StubAdapter 怎么改？
    返回一个故意错误的 SQL，例如 SELEC * FRM users。

    - 修改 System Prompt 的某一部分（比如去掉 Few-shot 示例、或者改约束条件），再跑一遍同样的 10 个问题
    - 对比两版 Prompt 的准确率

- Few-shot 示例对准确率影响有多大？
    normal: 10/10
    few-shot: 10/10 没有影响。

- 如果用户的数据库是中文字段名（如 `订单金额`），你的 Prompt 需要怎么调整？
    Prompt 需要明确告诉模型：只用 Schema 中真实存在的表名和字段名，不能把中文字段自行翻译成英文。

- 有没有办法让系统 **自动选择** 最合适的 Few-shot 示例？
    建立一个 Few-shot 示例库，每个示例保存自然语言问题和对应的正确 SQL。用户提出新问题后，先对问题生成 embedding，再和示例库中的问题做语义相似度搜索，选出最相关的 Top-K 示例加入 Prompt。

3-5
1. 当前的 `execute_sql` 是同步阻塞的。如果用 `asyncio.to_thread()` 把它扔到线程池里，能解决阻塞问题吗？有什么副作用？
    asyncio.to_thread() 可以缓解 execute_sql 对事件循环的阻塞，因为它会把同步数据库查询放到线程池中执行，
    让 FastAPI 的主事件循环可以继续处理其他请求。不过它并没有把同步代码真正变成异步代码，
    只是把阻塞转移到了线程池。副作用包括：线程池数量有限，大量慢查询可能把线程池占满；每个线程会有额外的内存和上下文切换开销；
    超时和取消也更难处理；如果数据库驱动或连接对象不是线程安全的，还需要特别注意资源隔离。因此它适合做短期改进，
    但更长期的方案通常是使用真正的异步数据库驱动或把复杂查询交给后台任务系统。

2. 如果用户问了一个和数据完全无关的问题（比如 “今天天气怎么样”），当前系统会怎么处理？你觉得应该怎么处理？（提示：这和第 9 节课 Query Router 有关）
    会把用户问题直接送到 Text-to-SQL 流程，可能被 LLM 强行生成一条 SQL。在 Text-to-SQL 之前增加一个 Query Router，
    先判断用户的问题属于哪种类型，例如数据查询、普通对话、文档问答或其他工具请求。只有数据查询才进入 Text-to-SQL。

3. 当前 Schema 自省结果是 JSON 格式。如果改成 DDL 格式（`CREATE TABLE orders (...)`）喂给 LLM，SQL 生成的准确率会变高还是变低？为什么？
    有可能。LLM 在训练数据中见过大量 CREATE TABLE 形式的 SQL，因此 DDL 更接近模型熟悉的数据库表示方式，也能更自然地展示字段类型、主键和约束。

4. `LLMResponse` 里返回了 `usage`（token 用量）。如果你要实现按 token 计费，这个数据应该存在哪个表里？和 `QueryExecution` 是什么关系？
    只保存在 API response 中。直接在 QueryExecution 表中增加 prompt_tokens、completion_tokens 和 total_tokens 字段，
    因为当前一次 QueryExecution 基本对应一次 Text-to-SQL 的 LLM 调用，这样能把 SQL 执行记录和对应的 LLM 成本关联起来。

5. 本节课的 `_format_answer` 是规则模版。如果用 LLM 来生成自然语言解释，需要额外调一次 LLM。成本翻倍值得吗？什么场景下值得、什么场景下不值得？
    如果查询结果比较复杂，例如有很多列、多组聚合结果、趋势变化，或者用户需要业务层面的总结和解释，那么额外调用一次 LLM 可能值得，但是其他情况下，不值得。
