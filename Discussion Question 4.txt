4-1 
### 实现列名校验（L2 扩展）
要求：
- 在 `validate_sql` 中新增列名校验：SQL 引用的列必须在 Schema 自省结果中存在
- 需要新增参数 `allowed_columns: dict[str, list[str]]`（表名 → 列名列表）
- 测试用例：故意在 SQL 里引用不存在的列名，验证被拦截

思考题：
- 如果用户用了 `SELECT *`，你怎么判断它引用了哪些列？
    使用Schema展开， 找出 *对应的表，然后用allowed_columns[表名]查到其引用的完整列清单。
- 如果 SQL 里有列别名（`AS total_sales`），别名不在原始 Schema 里，你会怎么处理？
    如果 SQL 中存在通过 `AS` 定义的列别名，例如 `SUM(amount) AS total_sales`，我不会直接拿别名 `total_sales` 去原始 Schema 中查找，因为它是 SQL 查询过程中生成的名称，并不是数据库中的实际列。我的处理方式是：首先，在定义别名时，检查 `AS` 左侧表达式中引用的原始列是否合法，例如确认 `amount` 是否存在于 `orders` 表中，并且具有访问权限。验证通过后，将 `total_sales` 记录为当前 SELECT 查询作用域中的合法别名。之后，如果 SQL 在 `ORDER BY` 等允许使用 SELECT 别名的位置引用了 `total_sales`，就检查它是否属于当前作用域中已定义的合法别名。如果是，就允许引用，不需要再次回到原始 Schema 中检查。不过，还需要考虑 SQL 的作用域和语法规则，例如 PostgreSQL 不允许在同一层查询的 `WHERE` 子句中直接引用 SELECT 定义的别名，因此不能简单地放行所有别名引用。这样既能避免把合法别名误判为不存在的列，也能保证 SQL 的 Schema 校验和语法约束。

4-2
### 实现错误自修复（retry with feedback）
要求：
- 当 SQL 执行失败时（如语法错误），把错误信息反馈给 LLM，让它重新生成 SQL
- 最多重试 2 次
- 每次重试都要经过安全校验
- 在 QueryExecution 中记录重试次数

思考题：
- 如果 LLM 连续 3 次都生成有语法错误的 SQL，你怎么告诉用户？直接说 “生成失败” 还是给出更具体的建议？
    给出更具体的建议，因为系统面向的是通过自然语言查询数据库的用户，他们不一定了解 SQL，因此应该建议用户如何调整自然语言问题，而不是要求他们修改 SQL。例如，如果无法识别表或字段，可以提示用户明确查询对象或使用数据库中存在的业务概念；如果 SQL 存在语法错误，可以提示用户简化问题或将复杂查询拆分成多个步骤；如果查询超时，可以建议缩小时间范围或减少返回的数据量。同时，系统会在 QueryExecution 中记录失败状态（status="failed"）、数据库原始错误信息、最后一次生成的 SQL 和重试次数，方便开发者排查问题。对普通用户只展示必要的解释和操作建议，避免暴露数据库结构或敏感错误信息。当前接口为了透明仍会返回生成的 SQL，面向普通用户的前端可以选择不展示。

- 重试会增加 LLM 调用次数（成本）。怎么控制重试成本？
    首先，限制重试次数（2 次）。其次，根据错误类型决定是否需要重试：对于 SQL 语法错误、字段引用错误等可能通过重新生成 SQL 修复的问题，把数据库的原始报错反馈给 LLM，让它知道具体错在哪里（给用户看的则是处理过的友好提示）；但对于数据库连接失败、权限不足等无法通过修改 SQL 解决的问题，应直接停止重试。第三，可以使用成本更低的模型完成 SQL 修复，并且只向模型提供相关的 Schema、错误信息和必要的上下文，而不是每次重新发送完整的数据库结构。但这里有一个取舍：如果错误是"表不存在"，原因可能正是 Table Selection 漏选了表，这时应该退回全量 Schema，所以当前实现在重试时使用的是全量 Schema。此外，如果连续生成相同的错误 SQL，可以提前终止重试，避免重复消耗 Token。最后，可以缓存经过成功执行和校验的 SQL，并且只在执行成功后才写入缓存，避免把失败的 SQL 缓存下来，使相同问题能够复用已有结果，减少不必要的 LLM 调用。（其中"按错误类型决定是否重试"和"相同错误提前终止"是改进方向，当前实现对所有执行错误都会重试。）


4-3
### 用异常类型替代字符串匹配做错误分类
当前 `_classify_error` 是字符串匹配 `"syntax error" in error_msg`。
要求：
- 用 `psycopg2.errors` 的具体异常类型（如 `SyntaxError`、`UndefinedTable`、`InsufficientPrivilege`）来分类
- 对比字符串匹配和异常类型匹配的准确率差异

思考题：
- 如果用户的数据库是 MySQL 而不是 PostgreSQL，`psycopg2.errors` 还能用吗？你怎么做跨数据库的错误分类？
    不能。psycopg2 是 PostgreSQL 专用的驱动，psycopg2.errors 里的异常类只有连接 PostgreSQL 时才会抛出；MySQL 使用 pymysql 等驱动，异常类型和错误号完全不同。
    跨数据库的做法：按数据库类型分别写分类器（如 classify_postgres、classify_mysql），内部使用各自驱动的异常类或错误号，但统一输出同一套错误类型（syntax_error、undefined_table 等），让上层的 chat.py 和重试逻辑只认这套统一的类型，不需要关心底层是什么数据库。分类时也可以优先使用 SQL 标准定义的 SQLSTATE 错误码（如 42601 表示语法错误、42P01 表示表不存在），它不依赖报错文字，比字符串匹配更可靠。对于暂时没有专门分类器的数据库，可以退回字符串匹配作为兜底，当前实现就是这样处理非 PostgreSQL 异常的。

4-4
### 给安全校验加敏感列过滤
要求：
- 新增配置项 `SQL_SENSITIVE_COLUMNS`（如 `["password", "ssn", "salary", "credit_card"]`）
- 如果 SQL 引用了敏感列，拦截并提示 “该列包含敏感信息，不允许查询”
- 支持全局配置和 per-DataSource 配置

思考题：
- 如果列名是 `pwd` 而不是 `password`，你的关键字匹配还有效吗？
    没有。

- 更好的方案是什么？（提示：基于列的 `comment` 或类型来判断，而不是列名）
    更好的方案是根据列的元数据判断，而不是只看列名。第一，使用列的 comment：由 DBA 在数据库中给敏感列加上标记，例如 COMMENT ON COLUMN users.pwd IS '[sensitive] 登录密码'。Schema 自省时已经读取了列的 comment（ColumnSchema.comment），校验时检查是否带有 [sensitive] 标记即可，不受列名影响。第二，根据数据类型或数据格式判断，例如 bytea 类型、以 $2b$ 开头的 bcrypt 哈希、符合身份证号或信用卡号格式的数据，可以抽样后用正则识别。第三，在数据库层面限制权限，给数据源配置只读账号，通过列级权限（GRANT SELECT (id, email) ON users）或视图，让该账号根本无法访问敏感列。应用层校验只是其中一层，数据库权限才是最后一道防线。实际项目中通常组合使用：以 comment 标记为主，关键字匹配作为兜底，再配合数据库权限控制。


4-5
1. 当前安全校验只拦截了 “LLM 生成的危险 SQL”。但如果攻击者直接调你的 API，在 `message` 字段里传入 `"; DROP TABLE users; --"`，你的系统会怎么处理？（提示：这不是 Prompt Injection，是经典 SQL Injection。你的代码是否安全？）
    安全。因为这个messahe是作为自然语言给LLM让LLM生成SQL指令的，所以validate_sql还是会拦截危险的指令的。

2. `sqlglot.parse()` 如果遇到非常长的 SQL（比如 100KB），解析时间可能很长。你怎么防止恶意用户用超长 SQL 做 DoS 攻击？
    可以设置一个SQL长度限制，避免非常长的SQL进入解析器。也可以设置超时系统，时间太长就停止运行。

3. 当前的 `allowed_tables` 来自 Schema 自省。如果用户的数据库有 `pg_catalog` 系统表，自省是否会把系统表也列出来？如果会，L2 校验还安全吗？
    如果 Schema 自省把 pg_catalog、information_schema 等系统表也加入 allowed_tables，那么当前的 L2 校验就不够安全。因为 L2 只检查 SQL 中引用的表是否存在于白名单中，如果系统表本身也在白名单里，就可能被正常放行。因此，在 Schema 自省阶段就应该排除系统 schema，只保留真正允许用户访问的业务表，例如 PostgreSQL 中通常只允许 public schema，或者由系统显式配置允许访问的 schema。

4. LLM 自然语言解释目前是 “每次多调一次 API”。如果要把解释结果缓存起来（同样的 SQL + 同样的结果 → 同样的解释），你会用什么做 cache key？纯用 SQL 文本够吗？
    不，因为纯SQL文本可能到时相同SQL在不同时间执行时数据库中的数据变化而产生不同结果。cachekey可以用标准化的SQL+查询结果作为cachekey，更加保险。

5. 本节课的安全校验是 **事后拦截**（LLM 先生成 SQL，然后校验）。有没有 **事前预防** 的方案？（提示：能不能让 LLM 根本生成不出 DELETE？Function Calling / Structured Output 了解一下）
    可以一个模板，让llm按照预先定义好的结构返回查询意图。例如，可以限制模型只能返回 SELECT 类型的操作，并且只能从允许的表名、列名、聚合函数和排序方式中选择。后端再根据这个结构生成真正的 SQL。
