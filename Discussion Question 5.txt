### 作业 1：语义相似度缓存
要求：
- 用 OpenAI 的 `text-embedding-3-small` 给用户问题生成 Embedding
- 用余弦相似度在缓存中查找最相似的历史问题
- 相似度 > 0.95 时命中缓存
- 对比精确匹配和语义匹配的命中率差异

思考题：
- Embedding 缓存和 SQL 缓存应该用同一个 Redis 实例吗？
    在项目规模较小时，Embedding 缓存和 SQL 缓存可以使用同一个 Redis 实例，通过不同的 key 前缀（例如 sql_cache: 和 sem_cache:）进行区分，这样实现比较简单，也方便维护。但是随着缓存规模扩大，最好将两者分开管理。首先，Embedding 缓存的数据量明显大于 SQL 缓存，例如一个 1536 维的 Embedding 以 JSON 格式存储可能占用数十 KB，而一条 SQL 通常只有几百字节。如果 Redis 内存不足，大量 Embedding 可能导致 SQL 缓存被提前淘汰，降低缓存命中率。其次，两种缓存的访问方式不同：SQL 缓存通常可以通过 key 直接查找，而语义缓存需要计算向量相似度。如果每次都读取所有 Embedding 并逐一比较，随着数据量增加，查询效率会下降，因此可以考虑使用 Redis 向量索引或 pgvector 优化检索。最后，两种缓存的生命周期也不完全相同。SQL 缓存可能因为数据库 Schema 变化而失效，但问题本身的 Embedding 不一定需要重新计算。因此，大规模情况下将两者分开管理，可以更灵活地设置内存限制、缓存过期时间和失效策略，提高系统性能与资源利用率。
- 如果用户的问题带了时间条件（“今天的销售额” vs “昨天的销售额”），语义相似度很高但 SQL 不同，怎么处理？
    对于带有时间条件的问题，不能只根据 Embedding 的余弦相似度判断是否命中缓存，因为语义相近的问题不一定具有相同的查询条件。例如，“今天的销售额”和“昨天的销售额”在语义上非常接近，但查询的日期不同，因此不能直接复用相同的查询结果。我的处理方式是，在语义匹配之前或之后增加约束条件检查，使用 `extract_constraints` 提取问题中的日期、时间范围和数字条件，只有这些关键条件一致且语义相似度超过设定阈值（0.95）时，才允许命中缓存。对于“今天”“昨天”“上周”等相对时间表达，还可以先将其转换为具体日期，再生成缓存 key 或进行匹配，以避免不同日期的问题发生误命中。另外，即使用户再次提出完全相同的“今天的销售额”，如果缓存保存的是查询结果，第二天也不能继续使用昨天的结果，因此需要为这类缓存设置较短的有效期，例如当天结束时过期。更进一步，可以使用参数化 SQL，将查询逻辑与具体日期分开，例如缓存 `WHERE created_at >= :start_date` 这样的 SQL 模板，每次执行时根据用户的问题填入对应日期。这样既可以提高缓存复用率，也能保证时间条件的正确性。

### 作业 2：动态上下文窗口

要求：
- 当前 `max_history_turns` 是固定 5 轮
- 改为动态：根据 Prompt 的 token 总量决定保留多少轮（不超过模型 context window 的 70%）
- 用 `tiktoken` 估算 token 数量

思考题：
- 如果历史上下文和 Schema 加起来已经占了 80% 的 context window，你会砍历史还是砍 Schema？为什么？
    我会优先裁剪较早的历史对话，但保留最近一到两轮，因为历史主要用于理解追问，而 Schema 是生成正确 SQL 的基础，缺少相关表或列可能导致 SQL 错误。
    对于 Schema，我会通过 Table Selection 筛选相关表，而不是直接截断。同时，可以将较早的对话压缩为摘要，删除查询结果中的冗余数据，并简化 Schema 描述，以减少 Token 消耗。
    总体原则是优先保留必要的 Schema 和最近的相关历史，在保证 SQL 正确性和上下文连贯性的前提下控制 Token 成本。

### 作业 3：可修复 vs 不可修复的错误分类

要求：
- 在 `retry_with_feedback` 中区分 “可修复错误”（语法错误、方言不对）和 “不可修复错误”（连接失败、权限不足）
- 不可修复的错误直接返回，不浪费重试次数
- 定义至少 5 种错误类型并分类

思考题：
- “表不存在” 是可修复还是不可修复？（提示：如果 Schema 里有这张表但名字大小写不对呢？）
    “表不存在”属于条件性可修复错误，需要根据具体原因判断。如果表确实不存在于数据库 Schema 中，就无法通过重试修复，应直接返回错误。如果表实际存在，只是 SQL 中的表名大小写、Schema 前缀或引用方式不正确，就可以将错误信息反馈给 LLM，重新生成 SQL。
    由于系统在执行前会通过 L2 Schema 校验拦截不存在的表，因此执行阶段遇到的这类错误更可能是命名或引用问题。

### 作业 4：缓存命中率监控

要求：
- 在 Redis 中额外维护两个计数器：`cache_hit_count` 和 `cache_miss_count`
- 新增 API `GET /api/v1/stats/cache` 返回命中率
- 当命中率低于 20% 时在日志中输出 warning

思考题：
- 命中率低意味着什么？是缓存设计有问题，还是用户的问题太多样了？
    单看总命中率分不出来，要看按层拆开的数据，这正是加上两个分层计数器的原因：精确命中低、语义命中高：说明用户经常问同样的事，只是说法不同。缓存设计是对的，而且语义缓存起了作用。
    两层都低，日志里却有很多 sql.semantic_cache.miss best_similarity=0.93 这种"差一点就命中"的记录：说明是设计问题，阈值定得太严了。5-1 的实测里，0.95 的阈值下，"销售总额"和"总销售额"（0.886）都匹配不上。
    两层都低，最高相似度也普遍很低（比如 0.5）：说明用户的问题确实很分散，属于探索式分析，缓存本来就帮不上多少忙。
    还有一些是系统本身造成的未命中，命中率低不一定是用户的原因：数据源 Schema 变化后整个缓存会被清空；TTL 只有 1 小时，过期后就得重新生成；精确缓存是按数据源分开的，同一个问题换一个数据源，就必须重新生成。

- 你怎么提高命中率？（提示：TTL 调长？normalize 更激进？语义匹配？）
    更激进的规范化（成本最低）：去掉标点、空格、语气词（"请问"、"帮我查一下"），把全角字符转成半角。5-1 的实测里，"少了一个问号"就会导致精确匹配失败，这类情况靠规范化就能解决。
    调整语义阈值，但必须同时保留条件检查：5-1 的数据显示，阈值从 0.95 降到 0.85，命中率从 40% 提高到 50%；没有条件检查时，会出现 2 次误命中（今天/昨天、前 3/前 5），加上条件检查后误命中为 0。
    TTL 调长：缓存的是 SQL 而不是查询结果，SQL 本身不会因为新数据写入而过时，只有 Schema 变化时才会失效，而 Schema 变化时已经会主动清空缓存。所以 SQL 缓存的 TTL 可以设得比 1 小时长得多。例外是 SQL 里写死了具体日期的情况，这个在 5-1 讨论过。
    预热缓存：把最常见的问题（比如报表上固定要看的几个指标）提前生成好 SQL 放进缓存。
    但不要只盯着命中率这一个数字：命中率越高不一定越好，误命中一次（返回了错误的数据）的代价，远大于未命中一次（多调用一次 LLM）。所以提高命中率的前提，是先把误命中控制住。

5-5
请用文字回答以下问题：
1. 多轮对话中，如果第 1 轮的 SQL 结果是错的（比如表名改了导致查出空结果），第 2 轮的问题基于第 1 轮的错误结果，会发生什么？怎么处理？
    错误会沿着对话一直传递下去，而且不会报错。在当前实现中，历史上下文会把上一轮的 SQL 和结果（result_summary）一起交给 LLM，system prompt 还要求 LLM "把新的筛选条件应用到上一轮的查询模式上"。所以如果第 1 轮的 SQL 本身有问题（比如条件写错导致查出空结果），第 2 轮会在这个错误的 SQL 基础上继续修改，得到的结果同样是错的，但 SQL 能正常执行，用户很难察觉。
    检查代码时我还发现一个相关问题：_build_conversation_history 只要找到 QueryExecution 里的 SQL 就会放进历史，不区分这次查询是成功、失败还是被安全校验拦截。被拦截或执行失败的 SQL 也会以 "SQL: ..." 的形式出现在上下文中，LLM 可能误以为它执行成功了，并在下一轮沿用。
    处理方法：第一，历史中标注每一轮的状态，失败或被拦截的轮次要么不放入历史，要么明确写上"此查询失败/被拦截"；第二，对可疑结果做标注，例如结果为 0 行时，在历史中写明"Result: 0 rows（结果为空，可能条件有误）"，同时在回答中提醒用户确认；第三，给用户纠正的机会，例如提供"重新开始对话"或"基于第 N 轮重新提问"的入口，让错误的轮次不再进入后续上下文。

2. 语义缓存的 TTL 设为 1 小时。如果用户的数据库每分钟都有新数据写入，1 小时的缓存意味着用户可能看到最多 1 小时前的数据。这可接受吗？怎么让用户自己决定？
    首先需要区分缓存的是什么。当前系统缓存的是 SQL，而不是查询结果：命中缓存后只是跳过了 LLM 生成 SQL 这一步，SQL 仍然会在数据库上重新执行，所以用户看到的永远是最新的数据，1 小时的 TTL 并不会导致数据过时。SQL 缓存真正需要担心的是 Schema 变化（系统已在 Schema 变化时清空缓存）和 SQL 中写死了具体日期这两种情况。
    如果为了进一步提速而缓存查询结果，那么能否接受取决于使用场景：看月度报表时，几分钟甚至几小时前的数据通常可以接受；监控实时订单或库存时则不可接受。让用户自己决定的方式有：在请求中提供 use_cache 或 max_staleness（可接受的最大数据延迟）参数；按数据源配置 TTL，实时业务库设得短、离线数仓设得长；在回答中标明"数据更新于 X 分钟前"，并提供"刷新"按钮，让用户在需要最新数据时可以绕过缓存。

3. Table Selection 用 LLM 做精选时，LLM 可能选错表（选了不相关的表、漏了相关的表）。这比全量注入所有表更糟吗？什么时候应该放弃 Table Selection 直接全量？
    漏选相关的表比全量注入更糟，多选不相关的表则影响不大。漏选时 LLM 看不到需要的表，要么生成失败，要么用一张看起来相似但不正确的表凑合——而安全校验 L2 使用的是全量表名单，这样的 SQL 能通过校验并正常执行，返回的是错误的数据。多选不相关的表只是多消耗一些 token，偶尔会干扰 LLM。

    我在验证 8.5 时实际遇到了这个问题：关键词匹配因为"中文问题 + 英文表名"完全匹配不到；LLM 选表时返回的不是纯 JSON，解析失败；最后退回兜底逻辑"取前 3 张表"，只是因为 demo_orders 恰好排在第一位，答案才是对的。这说明选表失败时取前 N 张表相当于随机选表。

    应该放弃 Table Selection、直接全量注入的情况：一是 Schema 的 token 数远小于预算时，比如 gpt-4o 的预算接近 9 万 token，几十张表全量注入完全没问题，判断标准应该是 Schema 的 token 数而不是表的数量；二是选表失败或结果不可信时，应该退回全量而不是前 N 张；三是执行报"表不存在"后重试时，应该使用全量 Schema（当前实现已经这样做）；四是追问类问题，历史中已经涉及的表必须保留。Table Selection 本质上是节省成本的优化，只有在 Schema 大到放不进上下文时才值得使用。


4. 错误自修复中，LLM 看到了自己之前的错误 SQL 和报错信息。如果 LLM “修正” 后的 SQL 仍然报同样的错，第二次重试有意义吗？怎么避免 “原地踏步” 的重试？
    如果第二次生成的 SQL 和第一次完全相同，或者报的是同一个错误，那么第二次重试基本没有意义，只是在浪费 LLM 调用。在 4-2 的测试中，模拟 LLM 连续两次生成相同的错误 SQL，两次都报 function avg(character varying) does not exist，第二次重试没有带来任何改善。此外，当前实现每一轮只把"最近一次"失败的 SQL 和报错反馈给 LLM，它看不到更早的尝试，可能在两个错误版本之间来回切换。
    避免原地踏步的方法：第一，提前终止——把新生成的 SQL 规范化后与之前的尝试比较，相同就直接停止；错误类型和报错信息与上一轮相同，也停止或改变策略。第二，把所有失败的尝试都放进提示中（"以下写法都已失败：……"），让 LLM 知道哪些方向行不通。第三，每次重试换一种策略，例如第二次换用更强的模型、补充全量 Schema，或者根据报错给出更具体的提示（比如找到大小写正确的表名直接告诉 LLM）。第四，结合 5-3 的分类，不可修复的错误一次都不重试。


5. 本节课的五个优化（多轮 / 重试 / 缓存 / Table Selection / 多方言）都是独立的。如果产品经理说 “这周只能上一个”，你怎么排优先级？用什么标准？
    我的标准是：影响面 × 严重程度，再除以实现成本和上线风险。影响面指有多少用户、多少请求会遇到这个问题；严重程度指遇到时是"查询失败"、"返回错误数据"，还是"只是慢一点或贵一点"；风险主要看这个优化有没有可能引入新的错误。
    排序前我会先用数据说话，查询 query_executions 表：失败率（status=failed）是多少、有多少问题是"哪个最高""它占多少"这种依赖上一轮的追问、重复问题的比例、各数据源 Schema 的大小、有多少用户使用 MySQL。
    在没有特殊数据的情况下，我会优先上线多轮对话：数据分析天然就是连续追问的过程，没有多轮对话时"哪个最高？"这类问题会完全答错，影响面最大，而且实现风险低。其次是错误自修复，它直接降低失败率，结合 5-3 的分类后成本也可控。缓存主要节省成本和延迟，用户量上来之后才明显，而且有误命中返回错误数据的风险，需要谨慎上线。Table Selection 只在 Schema 很大时才有收益，并且 8.5 的实测表明它在中文场景下不稳定，选错表的代价很高，应该排在后面。多方言要看客户情况，如果没有用户使用 MySQL，就可以暂缓；如果重要客户就是用 MySQL，那它会变成第一优先级，因为不支持就完全无法使用。
