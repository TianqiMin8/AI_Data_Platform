6-1
### 作业 1：实现 HTML 解析器
要求：
- 新增 `HtmlParser`，支持 `.html` 文件解析
- 用 `BeautifulSoup` 提取正文内容（去掉 `<script>` / `<style>` / 导航栏等）
- 注册到 `PARSER_MAP`
思考题：
- HTML 页面里的表格数据应该怎么处理？直接丢弃还是转成文本？
    表格数据不应该直接丢弃，因为价格、参数等重要信息经常保存在表格中。但也不能简单地拼接单元格，否则会丢失行列关系，影响检索准确性。我会将表格转换为带列名的文本，例如“产品：A；价格：100”，确保每行数据都有完整语义。也可以使用 Markdown 表格，但需要注意切块时保留表头。对于大型结构化表格，可以直接存入数据库，通过 Text-to-SQL 查询，提高准确性。

- 如果 HTML 里有大量广告和侧边栏，怎么只提取正文？（提示：`readability` 算法）
    我会采用分层过滤的方法。首先优先提取 <main> 或 <article> 等语义标签中的内容；其次根据 nav、aside 等标签以及 ad、sidebar 等 class 关键词删除无关区域。如果这些方法效果不好，可以使用 readability 算法，根据文本长度、段落分布、class/id 和链接密度判断正文区域。正文通常文字较多、链接密度较低，而广告和导航区域往往相反。不过 readability 对中文或短文本页面可能不够准确，因此可以设置最小文本长度检查，提取内容过少时使用备用方案。对于结构固定的网站，也可以使用专门的 CSS 选择器提高准确性。



6-2
### 作业 2：实现 chunk 去重
要求：
- 在 Pipeline 中加一步：如果新 chunk 的内容和已有 chunk 完全相同（同一个 Document 内），跳过
- 用哈希比较（`hashlib.sha256(content)`），不用字符串全文比较
思考题：
- 跨文档的 chunk 需要去重吗？（两个不同 PDF 有同样的一段话）
    跨文档的 Chunk 不应该直接删除，因为即使内容相同，它们也可能来自不同文档，具有不同的来源信息和访问权限。如果直接删除，可能导致引用来源丢失，或者删除某份文档时影响其他文档。更好的方法是共享相同文本和 Embedding 的存储，同时保留每个文档独立的引用关系和权限信息。在检索阶段，可以合并重复内容，并标注其所有允许访问的来源，避免重复结果占用检索位置。

- 去重的粒度应该是完全相同还是高度相似（>95%）？
    入库时我会优先去除完全相同的 Chunk，而不直接删除相似度超过 95% 的内容，因为高度相似的文本可能在日期、金额或版本号等关键信息上存在差异，直接删除可能造成信息丢失。可以先统一空格、字符格式等，再通过哈希判断是否重复。对于高度相似的内容，可以只做标记，或者进一步比较日期、数字等关键条件。在检索阶段再合并相似结果，提高结果多样性，同时保留原始信息。

### 作业 3：给 Chunking 加 token 计数
要求：
- 安装 `tiktoken`，在 Chunk 创建时计算并填充 `token_count` 字段
- 用 `tiktoken.encoding_for_model("text-embedding-3-small")` 获取编码器
思考题：
- `char_count=500` 对应大约多少 tokens？中文和英文有区别吗？
    中文和英文有明显区别。以 cl100k_base 分词器为例，500 个中文字符大约对应 470 个 tokens，而 500 个英文字符大约对应 115 个 tokens，实际数量取决于具体内容。这是因为 BPE 分词器可以将常见英文字符组合合并成一个 token，而中文通常需要更多 tokens。因此，按字符数切块会导致不同语言的实际 token 数量差异较大，影响 Embedding 成本和上下文空间利用率。更合理的方法是使用 count_embedding_tokens 按 token 数切块。

- 如果某个 chunk 的 token_count 超过了 Embedding 模型的最大输入长度，你怎么处理？
    text-embedding-3-small 的单条输入上限为 8191 tokens，超过后 API 会报错，还可能导致整个批次处理失败。我会优先在切块阶段检查 token 数量，将超长 Chunk 进一步拆分成多个符合限制的小块，并保留适当重叠，避免信息丢失。另一种方法是分段生成 Embedding 后取平均，但可能降低语义检索准确率。直接截断虽然简单，却会丢失部分内容，因此只作为最后的兜底方案。最好在调用 API 前就完成长度检查，避免不必要的失败和重试成本。


6-4
### 作业 4：文件去重（上传前检查）
要求：
- 上传文件时，计算文件内容的 SHA256 哈希
- 在 Document 表新增 `content_hash` 字段
- 如果同一个用户已上传过相同内容的文件，返回已有的 Document 而不是重新处理

思考题：
- 如果用户修改了 PDF 的一个错别字重新上传，哈希会变吗？应该怎么处理？
    哈希会发生变化，因为 SHA-256 对输入内容非常敏感，即使只修改一个字节，也会产生完全不同的哈希值。因此，系统可能将修改后的 PDF 识别为新文档，造成新旧版本重复存储，甚至检索到旧版本的错误内容。我会优先将其作为已有文档的新版本处理，通过文件名或文本相似度识别可能的版本更新，并让用户确认是否替换。同时，可以对提取的文本计算哈希，避免 PDF 元数据变化造成误判，并通过 Chunk 哈希复用未修改部分的 Embedding，只重新处理发生变化的内容，以降低成本。

- 文件名不同但内容相同，算重复吗？
    应该算重复，因为文件内容相同，哈希值也相同，与文件名无关。重复存储会增加空间和 Embedding 成本，也可能导致检索结果重复。因此，系统可以通过内容哈希识别重复文件，并返回已有文档的信息。不过，用户可能只是想重命名文件，或者在不同场景下使用同一份内容，因此可以提示用户选择重命名或保留独立的文档引用。相反，如果文件名相同但内容不同，则不属于完全重复，更可能是已有文档的新版本。

### 作业 5：思考题
请用文字回答以下问题：
1. 当前的 Chunking 是按文档全文切的。如果一个 PDF 有 “目录页” 和 “附录”，这些内容也会被切成 chunks 并参与检索。这有问题吗？怎么解决？
    有问题，尤其是目录页。目录页集中了整份文档的章节标题和关键词，却没有实际内容，用户提问时很容易因为关键词高度重合而排在检索结果前面，挤掉真正包含答案的正文。附录则不同，可能包含术语表、数据表等有用内容，不应一律删除。我会先识别再区别对待：通过“大部分行以页码结尾”“含有引导点或‘目录’字样”等特征，或利用 PDF 书签定位目录和附录的页码范围；目录页直接跳过不生成 Chunk，附录保留但在 metadata 中标记 page_type，检索时降低权重。此外，也可以允许用户在上传时指定导入的页码范围作为兜底。

2. RecursiveChunker 的 separators 是 `['\n\n', '\n', '。', '.', ' ']
`。如果处理的是代码文件（Python / Java），这些分隔符合适吗？你会怎么调？
    不合适。这些分隔符是为自然语言设计的，“。”在代码中几乎不会出现，“.”会把 obj.method() 这样的语句从中间切断，空格更会把代码切得支离破碎；即使是“\n\n”，也可能把一个函数从中间的空行处切成两半。我会根据文件扩展名选择不同的分隔符，优先在语法单元的边界切分，例如 Python 使用 ['\nclass ', '\ndef ', '\n    def ', '\n\n', '\n']，Java 使用 ['\nclass ', '\npublic ', '\nprivate ', '\n\n', '\n']，并去掉“.”和空格。更进一步，可以用 tree-sitter 解析语法树，按完整的函数或类切块，并为每个 Chunk 附带文件路径、类名和函数签名等上下文，同时适当调大 chunk_size。

3. 当前的 Pipeline 是 “解析全部页面 → 切片全部内容 → 批量入库”。如果一个 500 页 PDF 在第 300 页解析失败，前 299 页的结果会被保留还是全部回滚？当前代码的行为是什么？你觉得应该怎样？
    当前代码会全部回滚，并且连失败记录都不会保留。PdfParser 逐页提取文本时没有对单页做异常处理，第 300 页出错后异常直接抛出，前 299 页的文本只在内存中，尚未写入数据库。Pipeline 虽然会把状态设为 failed 并记录错误信息，但随后重新抛出异常，FastAPI 的 get_db 遇到异常会回滚整个请求，连 Document 记录本身也被回滚，用户只会收到 500 错误，查不到失败原因。我认为应该：第一，保证失败状态能保存下来，标记 failed 后不再抛出异常，或先单独提交 Document 记录；第二，对每一页单独捕获异常，跳过失败的页面并记录页码，将文档标记为部分成功，而不是因为一页出错就让整份文档作废；第三，大文件分批处理、分批提交，中途失败时保留已完成的部分，并支持从失败处继续处理。（已修复第一点：现在 Pipeline 的处理过程放在 SAVEPOINT 中执行，失败时撤销已写入的 Chunk，但保留 Document 记录并标记为 failed，错误信息中注明失败的阶段，例如“[parsing] Stream has ended unexpectedly”，接口正常返回而不是 500。）

4. 本节课的 Document 状态机是 `pending → processing → completed / failed`。如果以后加上 Embedding 步骤，状态机应该怎么扩展？
    当前代码其实已经在生成 Embedding 前把状态设为 embedding，但 Document 模型上的注释仍是 pending → processing → completed → failed，需要同步更新。我会按处理阶段细化为 pending → parsing → chunking → embedding → completed，任一阶段出错都进入 failed，并增加 partial 表示部分成功。这样排查问题时可以直接知道卡在哪一步，也可以从失败的阶段重试，例如 Chunk 已经入库、只是 Embedding 超时，就只需重新生成向量，不必重新解析和切片。同时，Document 应增加 failed_stage 和处理进度字段（如已处理页数、已生成向量的 Chunk 数），方便前端显示进度。以后更换 Embedding 模型时，还可以增加 reindexing 状态。状态之间的转换也应集中管理，只允许合法的转换。

5. 如果用户上传了一个 50MB 的 PDF（300 页），同步处理需要 2 分钟。你会怎么改成异步？描述完整的方案（包括 API 怎么改、后台怎么跑、前端怎么知道完成了）。
    API 方面，上传接口只负责校验文件、计算哈希、将文件保存到持久化位置并创建 status=pending 的 Document 记录，然后立即返回 202 Accepted 和文档 id，不再在请求中执行解析和 Embedding。需要注意当前代码处理完就会删除临时文件，改成异步后必须持久保存文件；50MB 的文件也应边接收边写入磁盘，而不是一次读入内存。同时新增 GET /documents/{id} 接口查询单个文档的状态和进度。后台方面，使用 Celery、RQ 或 arq 等任务队列，直接用项目中已有的 Redis 作为消息队列，由独立的 worker 进程执行 Pipeline，在每个阶段更新状态和进度并分阶段提交，同时支持失败重试、超时控制和安全地重复执行。FastAPI 自带的 BackgroundTasks 也能实现异步，但服务重启时任务会丢失，只适合处理小文件。前端方面，最简单的是每隔几秒轮询 GET /documents/{id}，根据进度字段显示进度条，直到状态变为 completed 或 failed；需要更好的实时性时可以使用 SSE 或 WebSocket 推送。此外，可以结合 6-4 的内容哈希，如果同一个文件正在处理中，直接返回该记录，避免重复处理。
