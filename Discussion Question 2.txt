### 实现数据源的更新接口
    要求：
    - 实现 `PUT /api/v1/datasources/{id}`，支持修改 name / host / port / database_name / username / password
    - 如果修改了连接信息（host / port / database_name / username / password），自动调用 `test_connection` 验证新连接是否可用
    - 如果验证失败，拒绝更新并返回错误原因

- PUT 和 PATCH 有什么区别？这个场景用哪个更合适？
    PUT 用于完整替换一个资源，而PATCH用于对资源进行部分更新。这个场景里PATCH更合适，因为用户不一定每次都改全部的连接字段。

- 如果用户只想改名字，不想改密码，请求体里不传 password 字段，你怎么区分 “不改” 和 “改成空字符串”？
    更好的方式是不传password的话，改成None；或者使用 req.model_fields_set 检查。

### 给数据源列表加分页
    要求：
    - 当前实现的分页用的是 `offset + limit`（跳过型分页）
    - 改成 **cursor-based 分页**（游标型分页），用 `created_at` 或 `id` 作为游标
    - 返回格式包含 `next_cursor`，客户端下一次请求带上这个 cursor

- offset 分页在数据量大时有什么性能问题？
    会变慢。它需要定位之前的记录，然后跳过它们最后取想要的数目。且数据变化会导致 offset 不稳定。

- cursor 分页有什么局限？（提示：能不能跳到第 100 页？）
    不能直接跳到第100页，需要知道第0=99页最后一条记录的cursor，更适合滚动记录

### 重复邮箱注册的并发竞争
    当前注册逻辑：
    ```python
    # 1. 先查有没有
    result = await db.execute(select(User).where(User.email == req.email))
    if result.scalar_one_or_none():
        raise ValidationError("该邮箱已注册")
    # 2. 再插入
    db.add(User(...))
    ```

- 如果两个请求几乎同时注册同一个邮箱，会发生什么？（提示：两个请求都过了第 1 步的检查）
    因为如果没有UNIQUE约束，可能产生重复邮箱，如果有约束，邮箱需要 unique，所以第二个可能会在flush的时候抛出IntegrityError。

- 你会怎么修复这个竞争条件？给出至少两种方案
    1. 使用 database 的 UNIQUE ，并捕获IntegrityError。
    2. 使用 SERIALIZABLE 让并发事务表现得更像串行执行，用锁避免多个请求同时操作。

- 数据库的 UNIQUE 约束在这里起什么作用？它能完全替代代码层的检查吗？
    在这里起到无论应用代码怎么写、无论多少个并发请求，同一个 email 最终只能有一条记录。不能完全替代代码层检查，因为代码曾能够提前给用户报“邮箱已占用”提示。

### 加密 key 轮转
    当前实现：所有数据库密码都用同一个 Fernet key 加密。如果这个 key 泄漏了，所有密码都暴露了。

- 如果你需要更换 encryption_key（key 轮转），你会怎么做？写出完整的步骤
  提示：你不能直接改 key，因为旧数据是用旧 key 加密的，新 key 解不开
    1. 生成新的Fernet key：new_key，在轮转期间也保留old_key
    2. 读取数据库中所有由old_key加密的密码
    3. 对每条数据：用old_key解密，用new_key加密，将新密文写回数据库
    4. 随机取样数据，确认可以用new_key解密
    5. 将应用的主加密key换成new_key
    6. 再次确认所有实例用的是new_key，没有依赖old_key的数据
    7. 禁用old_key

- 生产环境中，加密 key 应该存在哪里？（提示：不是 `.env` 文件）
    放在专门的secret management里，如AWS KMS / AWS Secrets Manager，在应用启动时通过运行环境的身份和权限取读取密钥。

1. 本节课的数据模型中，`Conversation.datasource_id` 是 nullable 的。这意味着一个对话可以不关联数据源。想一想：什么场景下对话不需要数据源？（提示：这个平台不只有 Text-to-SQL）
    对话不一定要连接数据库，也可能只是普通使用llm来进行问答。如上传PDF文件行让llm分析就不用关联数据库。

2. `Message.role` 用的是字符串而不是数据库 Enum。如果用 Enum，加一个新 role（比如 `tool`）需要做什么？用字符串呢？哪种方式在迭代速度上更有优势？
    如果用Enum，加一个新role需要修改数据库Enum的类型，并执行数据库migration和可能要修改schema。
    用string的话数据库结构本身不需要改变，只需要修改应用层代码，使系统能识别和处理新role。
    所以string在迭代速度上更有优势。

3. `QueryExecution.result_summary` 存的是摘要而不是完整结果集。如果一条 SQL 查出来 50000 行数据，完整结果应该存在哪里？怎么让前端能分页展示？
    完整结果应该存在其他文件存储系统如google cloud中，并保存位csv，json或者parquet文件。
    如果希望前端分页展示结果，也可以把结果放在专门的结果存储中，然后提供分页 API，例如：GET /query-executions/{id}/results?cursor=xxx&limit=100，前端第一次只获取前 100 行，用户继续翻页时再请求下一批数据

4. 本节课的认证用的是 JWT（无状态）。如果用户改了密码，已经签发的 Token 还有效吗？如果你想实现 “改密码后让所有旧 Token 失效”，你会怎么设计？
    一般有效。JWT是无状态，所以服务器验证只会检查token的签名和国企时间，不会检查这个token是否在用户修改密码前发的。
    如果要实现改密码后让所有旧 Token 失效，可以在在 User 表中保存：password_changed_at，然后用它和token.iat比较，如果token.iat < user.password_changed_at， 说明 Token 是在密码修改之前签发的，可以拒绝该 Token。

5. Schema 自省目前是同步阻塞的。如果用户的外部数据库有 1000 张表，自省可能要 30 秒。这时候怎么办？（提示：参考课程大纲中的 “异步任务” 模块）
    用户请求 Schema 自省 -> API 创建异步任务 -> 立即返回 task_id -> 任务队列 -> Worker 执行 Schema introspection -> 保存结果 -> 前端获取任务状态 / Schema
