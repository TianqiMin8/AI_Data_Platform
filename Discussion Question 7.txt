### 作业 1：实现 Embedding 缓存
要求：
- 对同一段文本（content hash 相同），不重复调用 Embedding API
- 用 Redis 缓存：`embedding_cache:{sha256(content)[:16]}` → 序列化的向量
- 文档重新导入时先查存
思考题：
- Embedding 缓存需要 TTL 吗？Embedding 模型不变的情况下，同一段文本的向量永远一样。
    从正确性来说，Embedding 缓存不一定需要 TTL，因为模型不变时，相同文本生成的向量通常保持一致，不会像 SQL 缓存一样因为 Schema 变化而失效。但从内存管理角度，建议设置较长的 TTL，例如 30 天，避免大量不再使用的向量长期占用 Redis 内存。对于经常访问的内容，可以在命中时刷新 TTL。此外，也可以通过 Redis 的 LRU 淘汰策略控制内存使用。

- 如果换了 Embedding 模型（从 `text-embedding-3-small` 换到 `text-embedding-3-large`），缓存还能用吗？
    不能直接复用，因为不同模型生成的向量属于不同的语义空间，即使维度相同，也不能直接混用。例如，text-embedding-3-small 默认生成 1536 维向量，而 text-embedding-3-large 默认生成 3072 维向量。因此，应该在缓存 key 中加入模型名称和维度，避免读取旧模型的缓存。同时，数据库中已有的文档向量也需要重新生成，并根据新维度调整数据库结构。重建期间应保持查询向量和文档向量使用同一模型，完成后再切换到新模型。

### 作业 2：实现按文档过滤的检索
要求：
- 当 `SearchRequest.document_ids` 不为空时，只在指定文档的 chunks 中检索
- 验证：上传两个不同文档，搜索时指定其中一个的 ID，确认只返回那个文档的 chunks
思考题：
- 如果用户想搜索 “某个文件夹下的所有文档”，当前的数据模型支持吗？需要加什么？
    当前不支持。因为 Document 只有 user_id，没有文件夹相关字段，无法直接按文件夹筛选文档。我会新增 folders 表，包含 id、user_id、name 和 parent_id，用于管理文件夹及其嵌套关系，并在 documents 表中增加 folder_id 外键。同时，在 SearchRequest 中增加 folder_id 和 include_subfolders 参数，通过 SQL JOIN 过滤指定文件夹内的文档。如果需要搜索子文件夹，可以使用 PostgreSQL 的 WITH RECURSIVE 查询所有子文件夹。此外，还需要检查用户权限，确保只能检索有权访问的文档。

### 作业 3：搭建一个简单的检索质量评估
要求：
- 准备 10 个测试问题 + 每个问题的 “正确 chunk ID”（人工标注）
- 写一个脚本，跑 10 个问题，统计 “正确 chunk 是否在 Top-3 结果中”（Hit@3）
- 分别测试 vector / bm25 / hybrid 三种方法的 Hit@3
思考题：
- Hit@3 = 70% 意味着什么？10 个问题里有 3 个找不到正确答案。
    Hit@3 = 70% 表示在 10 道测试题中，有 7 道的正确 Chunk 出现在前 3 条检索结果中，另外 3 道没有命中。这意味着 RAG 系统可能因为缺少正确的上下文而无法回答，甚至生成错误信息。不过，10 道题的样本量较小，结果容易受到题目难度影响，因此需要扩大测试集，并分析不同类型问题的检索表现，才能准确评估系统性能。

- 怎么提高 Hit@3？（提示：调 chunk_size？调 vector_weight？加 Re-ranking？）
    首先，可以改进 BM25 的中文分词，例如使用 jieba，提高关键词匹配能力。其次，可以调整 Chunk Size，避免内容过大导致语义混杂，或过小导致上下文丢失。还可以在修复 BM25 后调整 Hybrid Search 的权重，结合向量检索和关键词检索的优势。此外，可以引入 Cross-encoder Re-ranking，对初步检索的候选结果重新排序，或者使用 Query Rewrite 改写模糊问题。最后，应通过包含不同难度问题的评估集反复测试，选择实际效果最好的方案。

### 作业 4：用 Cross-encoder 替代 LLM 做 Re-ranking
要求：
- 安装 `sentence-transformers`
- 用 `BAAI/bge-reranker-base` 模型替代 LLM 做 Re-ranking
- 对比 LLM re-ranking 和 Cross-encoder re-ranking 的速度和效果
思考题：
- Cross-encoder 和 Bi-encoder（用于生成 Embedding 的模型）有什么区别？
    Bi-encoder（如 text-embedding-3-small）分别将问题和文档编码成向量，再通过余弦相似度计算相关性。文档向量可以提前生成并缓存，因此适合大规模快速检索。Cross-encoder（如 BAAI/bge-reranker-base）则将问题和文档一起输入模型，直接输出相关性分数，能够更细致地判断两者的关系，但无法提前计算分数。因此，通常先用 Bi-encoder 召回候选文档，再用 Cross-encoder 进行精确排序。

- 为什么 Cross-encoder 更准但更慢？
    Cross-encoder 通常更准确，因为它能通过注意力机制直接分析问题和文档之间的词语对应关系，捕捉细微的语义差异，而 Bi-encoder 将文本压缩成独立向量时可能丢失部分细节。但 Cross-encoder 需要针对每个问题和候选文档组合重新运行模型，无法复用预计算的文档向量，因此计算成本更高、速度更慢。实际使用中通常只对少量候选文档进行 Re-ranking，以平衡准确率和效率。相比 LLM Re-ranking，Cross-encoder 通常速度更快、成本更低，也不需要解析 LLM 的文本输出。

### 作业 5：思考题
请用文字回答以下问题：
1. 当前的 Embedding 在文档导入时同步生成。如果一个 500 页 PDF 切出 1000 个 chunks，批量 Embedding 可能需要 30 秒。这会阻塞上传请求吗？怎么改成异步？
    会阻塞，而且要分两层看。对上传请求本身来说，Pipeline 在请求中同步执行，用户要等解析、切片和 Embedding 全部完成（30 秒以上）才能收到响应，很容易触发前端或网关超时。对整个服务来说，Embedding 调用 OpenAI 是异步的网络请求，等待期间事件循环仍可以处理其他请求；但 PDF 解析、切片和 tiktoken 计数都是同步的 CPU 计算，虽然写在 async 函数中，执行期间会卡住整个事件循环，其他用户的请求也会被阻塞。改成异步的方案与 6-5 第 5 题一致：上传接口只保存文件、创建 pending 状态的 Document 并立即返回 202 和文档 id；由任务队列（如使用项目已有的 Redis 搭配 arq 或 Celery）的独立 worker 执行 Pipeline，每个阶段更新状态和进度；前端轮询 GET /documents/{id} 或通过 SSE 获取完成通知。此外，worker 中可以把 1000 个 chunk 分成多批并发调用 Embedding API（控制并发数以避免限流），每批完成后立即写入数据库，这样既能缩短总耗时，失败时也只需重试未完成的批次；7-1 的 Embedding 缓存也能让重新导入时跳过已经生成过的向量。

2. `score_threshold=0.3` 是一个 magic number。你怎么确定这个阈值是合理的？有没有自动调优的方法？
    应该用评估数据来确定，而不是凭感觉设定。具体做法是在 7-3 的评估集基础上，记录每道题中相关 chunk 和不相关 chunk 的相似度分数，观察两者的分布：阈值应该落在两者之间，既不能把相关的 chunk 过滤掉（影响召回率），又要尽量挡住不相关的 chunk。评估集中还应该加入一些知识库里根本没有答案的问题，阈值合理时，这类问题应该返回空结果，让系统回答“找不到相关信息”，而不是拿无关内容生成答案。自动调优的方法是：用评估脚本在一组候选阈值（如 0.1 到 0.6）上逐个运行，计算召回率、精确率或 F1，选出表现最好的那个；以后更换 Embedding 模型或文档类型时重新运行一次即可。还需要注意，余弦相似度的绝对数值和模型有关，text-embedding-3 系列的分数通常集中在较窄的区间，换模型后同一个阈值可能完全不适用。更稳健的做法是使用相对阈值（例如只保留与第 1 名分数差距不大的结果），或者把阈值放在 re-ranking 之后：7-4 中 Cross-encoder 对相关段落的打分约为 0.99，对无关段落接近 0，区分度远高于余弦相似度，更适合用来判断“是否相关”。

3. 如果用户删除了一个文档（Document），它的 chunks 和 embeddings 会被 cascade 删除。但 pgvector 的 HNSW 索引会自动更新吗？还是需要手动 REINDEX？
    HNSW 索引会自动更新，不需要手动 REINDEX。pgvector 的 HNSW 索引和 PostgreSQL 的普通索引一样，INSERT、UPDATE、DELETE 时都会自动维护。删除 chunk 时，对应的索引条目会先被标记为失效，查询时自动跳过，之后由 VACUUM（通常是 autovacuum 自动执行）把它们从图结构中清理掉，并修复相邻节点的连接。只有在一次性删除大量数据之后，索引可能因为碎片变多而占用空间偏大、查询召回率略有下降，这时可以手动执行 VACUUM，或者用 REINDEX INDEX CONCURRENTLY 在不锁表的情况下重建索引。另外，我检查当前数据库时发现，chunks 表的 embedding 列目前并没有建立 HNSW 索引（迁移中只添加了 vector(1536) 列），所以现在的向量检索实际上是逐行扫描整张表计算距离，数据量小时没有问题，chunk 增多后会明显变慢，应该通过迁移添加 CREATE INDEX ... USING hnsw (embedding vector_cosine_ops)。

4. 当前的 BM25 用的是 PostgreSQL 内置的全文搜索。如果要支持中文 BM25，你需要做什么？（提示：`zhparser` 扩展、`jieba` 分词、Elasticsearch）
    首先要解决分词问题。7-3 的评估中，BM25 的 Hit@3 为 0%，原因是当前使用 to_tsvector('simple', ...)，它只按空格和标点切分，会把“可以申请无理由退货”这样一整段当成一个词，查询“无理由退货的期限是几天”自然匹配不上。可选的方案有三种：第一，在 PostgreSQL 中安装中文分词扩展 zhparser 或 pg_jieba，创建中文的全文检索配置，再把 to_tsvector 的配置从 simple 换成它；这种方式改动最小，但需要基于 pgvector 镜像自定义 Docker 镜像来安装扩展。第二，在应用层用 jieba 分词，入库时把分词结果（用空格隔开）存入一个新列，查询时同样先用 jieba 切分问题，数据库仍然使用 simple 配置；这种方式不需要安装数据库扩展，但要保证入库和查询使用相同的词典。第三，使用 Elasticsearch 搭配 IK 等中文分词器，它提供真正的 BM25 评分，适合数据量大、对关键词检索要求高的场景，但需要额外维护一套服务并保持与数据库的数据同步。无论选哪种，都应该为分词后的内容建立 GIN 索引，否则每次检索都要对所有 chunk 重新分词计算。还需要注意，PostgreSQL 的 ts_rank_cd 并不是严格意义上的 BM25，它没有考虑词在整个文档集合中的出现频率（IDF），如果需要标准的 BM25 评分，可以使用 Elasticsearch 或 ParadeDB 等支持 BM25 的扩展。

5. Hybrid Search 的 `vector_weight=0.7, bm25_weight=0.3` 是固定的。有没有办法根据查询 “自动选择” 权重？（提示：如果查询包含型号/编号等精确信息，应该加大 BM25 权重）
    可以根据查询的特征动态调整权重。最简单的是基于规则：如果查询中包含型号、订单号、错误码、SKU 等精确信息（例如用正则识别字母和数字混合的串，如 EA-2026-001），或者用引号括起了需要精确匹配的短语，就提高 BM25 的权重，例如调整为 0.3:0.7；如果查询是较长的口语化描述（如“东西坏了能不能换个新的”），则提高向量检索的权重。更进一步，可以让 LLM 或一个小型分类模型先判断查询类型，再选择对应的权重组合，并用评估集分别为每种查询类型调出最佳权重。另一种思路是使用 RRF（倒数排名融合），它只根据两路结果中的排名而不是分数来合并，每个结果的得分为 1/(k + 排名) 的累加，不需要设置权重，也避免了当前按最大值归一化分数的问题——当前实现中，如果某一路只返回一条很弱的结果，归一化后也会变成满分。此外，如果某一路完全没有返回结果（例如目前中文 BM25 几乎总是返回空），就应该直接使用另一路的结果，而不是继续按固定比例计算。
